# Page Object для Java Playwright

Применяй правила к PO, компонентам и использующим их тестам. Перед выбором локаторов изучи тестовый модуль, конфигурацию, зависимости и реальный интерфейс. Соблюдай соглашения проекта и границы задачи.

Записывай правила этого skill и последующие дополнения на русском языке. Сохраняй идентификаторы Java, названия API и технические обозначения в исходном виде.

## Структура и композиция

- Объявляй классы и поля `final`, кроме случаев, когда есть конкретная причина разрешить наследование или изменение значения поля.
- Конструктор PO принимает Playwright `Page` и только присваивает `this.page = page` и инициализирует поля PO с модификаторами `private final` (локаторы и компоненты). Запрещены переходы, взаимодействия с интерфейсом, проверки, ожидания и другие побочные эффекты. Выполняй их в явных методах PO. Используй существующее JUnit-расширение `@UsePlaywright` для управления жизненным циклом и передачи `Page`, если оно доступно.
- Переиспользуй функциональность через композицию вместо наследования. Выноси общие формы, шапку, навигацию и самостоятельные части интерфейса в компоненты. Не создавай `BasePage` или иерархию наследования ради переиспользования.
- Если у компонента есть контейнер в интерфейсе, храни корневой `Locator` в поле `final` и ищи дочерние элементы относительно него. Храни `Page` только при необходимости, например для возврата другого PO после перехода.
- URL страницы представляй публичным статическим полем типа `String` с именем `URL`. Используй `public static final String URL`, если явно не требуется присваивать новое значение во время выполнения. Базовый адрес получай из `TestConfig`, не дублируй адрес сервера строковым литералом. Метод `open()` переходит по `URL` и возвращает текущий PO.
- Получай настройки URL через `TestConfig` в порядке: системное свойство `rfr.<key>`, переменная окружения `RFR_<KEY>` (верхний регистр, точки заменяются подчёркиваниями), константа по умолчанию в коде. Сохраняй существующий интерфейс конфигурации. Генерируй данные через `RandomDataUtils`, если он доступен.

## Методы и цепочки переходов

- Метод перехода на другую страницу возвращает PO целевой страницы. Действие на текущей странице возвращает `this`.
- Метод доступа к компоненту возвращает компонент. Действие компонента над собой возвращает этот компонент; переход возвращает целевой PO.
- Один метод соответствует одному бизнес-действию. Объединяй заполнение связанных полей формы в один метод вместо отдельных методов заполнения каждого поля. Имя метода должно раскрывать конкретную форму или бизнес-действие: `fillRegistrationForm(...)`, `fillLoginForm(...)`, `fillCredentials(...)`, `register()`, `signIn()`. Названия `fillForm` и `submit` — лишь абстрактные примеры, не шаблон именования; избегай общих имён, скрывающих бизнес-смысл. Отправку формы оформляй отдельным бизнес-действием; возвращаемый тип соответствует фактически открывающейся странице.
- Сценарий теста читается одной цепочкой вызовов страниц и компонентов. Управление жизненным циклом и подготовку данных оставляй за пределами цепочки.
- Методы проверок содержат только проверки. Запрещены клики, заполнение полей, переходы, отправка форм, изменение состояния и вызовы методов действий. Каждый переход явно указывай в цепочке перед проверкой целевой страницы.
- Не создавай `checkPageLoaded` и аналогичные общие проверки загрузки страницы под другими именами. Используй web-first assertions конкретного ожидаемого состояния в нужном месте сценария: проверки Playwright автоматически ожидают выполнения условия. Не добавляй отдельные проверки загрузки или готовности в конструкторы и методы переходов.
- Используй условия Playwright с автоматическим повторением через `PlaywrightAssertions.assertThat(...)` (`isVisible`, `hasText`, `hasValue`, `hasURL` и другие), если пользователь явно не потребовал иной механизм проверок. Не заменяй их фиксированными паузами, ручным опросом или немедленными проверками JUnit значений локаторов.

## Шаги Allure и параметры

- Всегда добавляй `@Step` к методам бизнес-действий, переходов и проверок PO и компонентов. Конструкторам и методам, которые только возвращают компонент, шаг не нужен.
- Название шага описывает бизнес-смысл и включает значимые параметры, например `@Step("Проверить логин в профиле: {username}")`.
- Записывай параметры методов средствами Allure; используй именованные подстановки для полезного контекста отчёта. Поддерживай работоспособность AspectJ/Allure в сборке и сохранение имён параметров при компиляции.
- Маскируй или исключай пароли, токены и другие секреты из отчёта параметров. Не включай секреты в названия шагов. Если механизм не позволяет безопасно исключить секрет, используй явный `Allure.step`, записывающий только несекретные параметры, вместо аннотации, которая захватывает секрет.
- Не добавляй шаги в утилиты конфигурации и генерации случайных данных.

## Пример структуры

```java
public final class ProfilePage {
  public static final String URL = TestConfig.baseUrl() + "/profile";
  private final Page page;

  public ProfilePage(Page page) {
    this.page = page;
  }

  @Step("Открыть профиль")
  public ProfilePage open() {
    page.navigate(URL);
    return this;
  }

  @Step("Проверить логин в профиле: {username}")
  public ProfilePage shouldHaveUsername(String username) {
    assertThat(page.getByRole(AriaRole.TEXTBOX,
        new Page.GetByRoleOptions().setName("Username").setExact(true)))
        .hasValue(username);
    return this;
  }
}
```

Адаптируй имена, импорты и локаторы к реальному приложению. Пример цепочки регистрации с явными переходами: `open().openRegistration().fillRegistrationForm(...).register().shouldBeSuccessful().proceedToSignIn().openLogin().fillLoginForm(...).signIn().header().openProfile().shouldHaveUsername(...)`. Выделяй экран успешной регистрации в отдельный PO, только если это самостоятельная страница.

## Проверка результата

- Не определяй загруженный аватар только по префиксу `data:image/`: такой же источник может быть у флага страны. Ограничивай локатор компонентом аватара и проверяй соответствие выбранному файлу после reload, чтобы отличать превью от сохранённого изображения.
- Если тест проверяет точный текст локализованного серверного сообщения, явно задавай язык запросов в контексте этого теста. Не полагайся на язык установленного браузера и не расширяй ожидаемый текст несколькими переводами, если требование задаёт конкретный язык.

Скомпилируй и запусти соответствующий UI-тест, если необходимые сервисы доступны. Проверь единую цепочку вызовов, отсутствие действий в методах проверок, правильные возвращаемые типы переходов, композицию общей функциональности и запись ожидаемых шагов и параметров Allure. Сообщи фактический результат запуска и отсутствующие условия, если они помешали проверке.
